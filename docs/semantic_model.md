# Семантична модель `PharmaSalesGold`

Модель над gold-шаром (`whgold.dwh`) для Copilot і ad-hoc звітності. Зберігається як TMDL —
той самий формат, у якому Fabric тримає семантичні моделі в git integration, тож деплоїться
разом із репозиторієм, а не збирається руками в UI.

```
fabric-semantic-model/PharmaSalesGold.SemanticModel/
├── .platform                      -- метадані Fabric-айтема
├── definition.pbism
└── definition/
    ├── database.tmdl
    ├── model.tmdl                 -- культура uk-UA, перелік таблиць
    ├── expressions.tmdl           -- підключення до whgold (Direct Lake)
    ├── relationships.tmdl         -- 20 звʼязків
    ├── cultures/uk-UA.tmdl        -- синоніми для Copilot / Q&A
    └── tables/*.tmdl              -- 13 таблиць
```

## 1. Чекліст із `copilot_prompts.md` — як реалізовано

| Пункт | Реалізація |
|---|---|
| 1. Звʼязки агрегатів із вимірами | 20 звʼязків у `relationships.tmdl`, усі «багато до одного», однонаправлені (TMDL-типове) |
| 2. Сховати технічні колонки | усі `SK…ID`, `Id`, `CreatedBy`, `CreatedAt` мають `isHidden`; числові колонки під мірами теж приховані |
| 3. Календар як таблиця дат | `dataCategory: Time` + `isKey` на колонці `Дата`; **усі 7 агрегатів** звʼязані з календарем |
| 4. Міри бізнес-мовою | 35 мір: «Сума продажів», «Кількість упаковок», «Візити», «Списано», «Кейси»… |
| 5. Синоніми | `cultures/uk-UA.tmdl`: «виручка», «оборот», «медпред», «ЛПУ», «рецепти» + англомовні (`sales`, `revenue`, `visits`, `prescriptions`) |
| 6. Описи | `///`-коментарі на таблицях, колонках і мірах — Copilot читає їх при доборі полів |
| 7. Заборона підсумовування відношень | відношення реалізовані як `DIVIDE(...)`-міри, а не колонки: «Сума продажів на візит», «Частка повернень», «Середня знижка, %», «Призначень на пацієнта» — вони перераховуються на кожному рівні |

Додатково: `discourageImplicitMeasures` у моделі — користувач не зможе випадково перетягнути
приховану колонку й отримати неявну суму.

## 2. Що знадобилося змінити в gold

Місячні агрегати не мали жодної колонки з датою — тільки `YearMonth`/`YearNum`/`MonthNum`.
Звʼязати їх із календарем було нічим, а без цього не працюють ані квартали, ані порівняння
з минулим роком (пункт 3 чекліста) для шести агрегатів із семи.

**`V260828.1000__gold_add_month_date_key.sql`** додає `MonthStartDate` (перший день місяця)
у шість місячних агрегатів і в їхні `v*`. Після деплою потрібен один повний прогін gold:

```sql
EXEC [dwh].[spGoldFullLoad] @load_id = 'after_month_date_key';
```

Власні часові колонки агрегатів (`YearMonth`, `YearNum`, `MonthNum`) у моделі приховані —
увесь час береться з `Календар`, щоб Copilot не мав двох джерел періоду.

## 3. Іменування

| Таблиця gold | У моделі |
|---|---|

| `DimProduct` | Препарат |
| `DimClientAccount` | Клієнт |

| `DimWarehouse` | Склад |
| `AggSalesMonthly` | Продажі за місяць |
| `AggSalesDaily` | Продажі за день |
| `AggVisitMonthly` | Візити |
| `AggPrescriptionMonthly` | Призначення |
| `AggInventoryMonthly` | Рухи запасів |
| `AggAdverseEventMonthly` | Побічні явища |
| `AggPromoEffectMonthly` | Промо проти продажів |

Міри двох таблиць продажів названі по-різному («Сума продажів» проти «Сума продажів за день»),
щоб Copilot не плутав місячний і денний зрізи — вони по-різному трактують повернення.

## 4. Міри, що потребують уваги

| Міра | Чому нестандартна |
|---|---|
| `Клієнтів, що купували` | `DISTINCTCOUNT` по денному агрегату — коректна на будь-якому рівні (день, місяць, рік) |
| `Лікарів охоплено (місяць)` | `IF(HASONEVALUE(…))`: за кількох місяців одразу повертає порожньо замість завищеної суми |
| `Лікарів, що призначали (місяць)` | те саме |
| `Сума продажів на візит` | `DIVIDE` двох мір — перераховується, а не підсумовується |
| `Частка повернень` | `DIVIDE`; знаменник — валовий оборот (продажі + повернення) |

## 5. Деплой

### 5.0. Перед будь-яким варіантом

У `definition/expressions.tmdl` має стояти справжній SQL endpoint і **item id warehouse
`whgold`** — його видно в URL айтема у Fabric (`.../warehouses/<id>`) або через
**Workspace settings → ... → About**. Id — це GUID у форматі `8-4-4-4-12`:

```
dc20f929-0e9a-4619-9cf3-4a9fb9117c07    -- whgold, валідний
9dc20f929-0e9a-4619-9cf3-4a9fb9117c07   -- НЕВАЛІДНИЙ: у першому блоці 9 символів
```

`deploy_semantic_model.py` перевіряє це перед відправкою: якщо id зіпсований, скрипт
зупиниться й покаже довжини блоків. Без такої перевірки модель створюється успішно,
але всі таблиці лишаються порожніми, і причину шукають у Direct Lake чи правах доступу.

Endpoint у Fabric спільний для всіх warehouse одного воркспейсу, тому той самий рядок,
що в пайплайнах, підходить.

### 5.1. Через git integration — найпростіше, бо вже підключено

У воркспейсі `fcw-plt-dds-d-westeu-01` git уже налаштований (панель **Source control**).
Тоді:

1. закомітити `fabric-semantic-model/PharmaSalesGold.SemanticModel/` у гілку, на яку
   підписаний воркспейс (`main`);
2. у Fabric відкрити **Source control** → вкладка **Updates** → **Update all**;
3. модель зʼявиться як айтем `PharmaSalesGold`.

Два нюанси:
* Fabric очікує папку айтема (`*.SemanticModel`) відносно кореня, налаштованого в
  git integration. Якщо там указано корінь репозиторію, наш шлях `fabric-semantic-model/…`
  стане підпапкою воркспейсу — це підтримується (у вас уже є підпапка `SemanticModel`).
  Якщо айтем не підтягнувся — перенесіть папку в корінь або змініть Git folder у налаштуваннях.
* панель показує кількість незастосованих змін (у вас було 17) — спершу розберіться з ними,
  щоб `Update all` не перезаписав чужу роботу.

### 5.2. Через REST API — якщо git не варіант

> **Важливо для git-підключеного воркспейсу.** Якщо у воркспейсі увімкнена git integration,
> джерелом істини є репозиторій: айтем, створений повз git, наступна синхронізація
> прибере. Саме так модель зникла після успішного деплою 28.08. У такому воркспейсі
> користуйтеся 5.1, а API лишайте для середовищ без git.
>
> Другий підводний камінь: **створення** моделі через API падає з
> `PersonalGateway_ShortMessage_PublishingError` — Fabric не може привʼязати джерело
> до щойно створеного айтема. Обхід: створити порожню модель у UI
> (**New item → Semantic model** над `whgold`), а потім підвантажити визначення
> в наявний айтем — тоді працює гілка `updateDefinition`, де привʼязка вже є:
>
> ```bash
> python3 deploy_semantic_model.py --workspace <ws-id> --item-id <id моделі з URL>
> ```
>
> Цей шлях перевірений і працює: модель піднімається, Copilot відповідає на промпти.
> Але він тимчасовий — айтем існує лише у воркспейсі, і синхронізація його прибере.

`deploy_semantic_model.py` створює або оновлює айтем без Desktop і без git:

```bash
az login
cd fabric-semantic-model

# подивитись, які файли підуть у Fabric
python3 deploy_semantic_model.py --workspace 343bb55f-11c8-43a8-acba-3ad333a2d07a --dry-run

# власне деплой
python3 deploy_semantic_model.py --workspace 343bb55f-11c8-43a8-acba-3ad333a2d07a
```

Скрипт сам знаходить модель за `displayName`: якщо її немає — створює
(`POST /semanticModels`), якщо є — оновлює визначення
(`POST /semanticModels/{id}/updateDefinition`). Токен береться з `az account get-access-token`
або передається через `--token`. Потрібні права Contributor у воркспейсі.

Після створення Fabric може попросити облікові дані підключення:
**Settings → Data source credentials → Edit credentials** для `whgold`.

### 5.3. Power BI Desktop — чому не спрацювало

Desktop **не відкриває папку `*.SemanticModel`** — він відкриває файл проєкту `.pbip`,
який лежить поруч і посилається на цю папку. У нашій папці такого файлу немає, бо це
розкладка Fabric git integration, а не Power BI Project.

Але навіть із `.pbip` Desktop тут не найкращий шлях: модель має партиції
`mode: directLake`, а Direct Lake — це формат Fabric-айтема; підтримка в Desktop
обмежена й залежить від версії. Тому Desktop має сенс для **перегляду й правок**
(TMDL view), а не для деплою.

Якщо все ж потрібен локальний перегляд:
1. увімкнути в Desktop **Options → Preview features → Power BI Project (.pbip) save option**
   і **Store semantic model using TMDL format**;
2. створити пустий проєкт, зберегти як `.pbip` — і порівняти отриману розкладку з нашою:
   так буде видно, який саме `.pbip` очікує ваша версія Desktop;
3. деплоїти все одно через 5.1 або 5.2.

### 5.4. Альтернатива: Tabular Editor

TE3 відкриває TMDL-папку напряму й публікує через XMLA endpoint
(потрібен **read-write XMLA** в налаштуваннях ємності). TE2 працює зі старим форматом
`Model.bim`, тож для TMDL не підходить без конвертації.

### 5.5. Перевірка після деплою

1. модель відкривається у воркспейсі, у списку таблиць — 13 позицій;
2. **Refresh** не потрібен: Direct Lake читає дані з `whgold` напряму;
3. створити порожній звіт і перевірити міру «Сума продажів» у розрізі «Календар[Рік]»;
4. поставити три питання з [`copilot_prompts.md`](copilot_prompts.md) у Copilot.

Якщо модель створилась, але таблиці порожні — майже завжди це неправильний item id
warehouse у `expressions.tmdl` (див. 5.0) або відсутні облікові дані підключення.

## 6. Що навмисно не зроблено

* **RLS не налаштований** — для прототипа всі бачать усі регіони. Якщо потрібно
  обмежити представників своєю територією, це окремий крок (ролі + фільтр по `DimEmployee`).
* **Перспективи (perspectives) не створені** — модель невелика, 13 таблиць видно цілком.
* **Календар не має позначок майбутніх періодів** — у `DimDate` є дати на 10 років уперед,
  тож у візуалах без фільтра періоду буде довгий «хвіст» порожніх місяців. Для дашбордів
  варто одразу ставити фільтр по періоду.
